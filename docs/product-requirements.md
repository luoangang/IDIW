# 情报采集与持续监控平台需求说明

> 状态：第一阶段平台已实现，需求持续演进
> 最后更新：2026-09-19
> 最新建设基线：[爬虫工具包管理与执行平台技术规范](crawler-platform-technical-spec-v1.md)。当前运行实现采用独立数据库和文件交换协议，每个工具包一张结果表；已退役的实验系统不再兼容或迁移。本文其余部分仅保留需求演进背景，冲突时以新规范为准。
> 说明：本文档记录已经明确的产品需求、待确认事项和设计约束。后续架构、数据库、采集器与前端实现均以本文档为需求基线。

## 1. 产品定位

本系统最终面向企业用户和学者个人提供数据能力。第一阶段产品形态是一个部署在服务器上的独立采集服务，由其他系统或调用方通过 API 使用。

系统不是一次性搜索工具。用户提交关键词后，系统应创建可持续运行的监控任务，定期发现并保存与该关键词相关的新资料。

## 2. 核心使用流程

1. 用户输入一个关键词或主题，例如“人工智能”。
2. 用户为该监控任务选择一个或多个业务模块。
3. 选中模块后，系统默认启用该模块下当前全部可用来源。
4. 用户可以取消该任务不需要使用的个别来源。
5. 系统只运行该任务已经选择且当前处于启用状态的数据源。
6. 系统按照每日或用户配置的周期重复执行采集。
7. 每次执行采用增量方式，保存新发现的数据，并保留历史数据。

## 3. 目标用户

- 企业用户：持续关注技术、产业、竞争、政策或市场相关信息。
- 学者个人：持续关注研究主题相关的新闻、论文和专利进展。

第一阶段不直接建设面向终端用户的账户和交互系统。企业或学者将由后续上层应用间接使用采集服务提供的数据。

## 4. 业务模块

| 模块 | 当前定位 |
| --- | --- |
| 新闻 | 采集新闻、百科、搜索结果等时效性或背景性资料 |
| 论文 | 采集与关键词相关的学术论文和期刊信息 |
| 专利 | 采集与关键词相关的专利及其专业字段 |

三个模块共享监控任务、来源管理和运行调度能力，但采集器目录与资源数据在物理结构上相互隔离。

## 5. 已确认的核心需求

- 用户可以使用关键词创建持续监控任务。
- 一个关键词任务可以选择新闻、论文和专利中的一个或多个模块。
- 每个监控任务可以在所选模块内独立选择需要使用的具体数据源。
- 模块和来源的选择属于任务级配置，不由全局固定绑定。
- 任务选中模块时，默认启用该模块下当前全部可用来源。
- 用户可以在任务级别取消任意不需要的来源。
- 模块新增并启用采集源后，所有已选择该模块的既有监控任务默认自动启用该来源。
- 自动加入的新来源仍允许在具体监控任务中单独关闭。
- 系统需要支持每日执行以及其他可配置的定时周期。
- 系统需要重复访问多个数据源，并持续补充新数据。
- 历史数据需要保留，后续更新不能覆盖或丢失既有资料。
- 数据来源应采用可扩展、可管理的适配器机制。

## 6. 当前阶段范围

当前项目处于第一阶段。本阶段目标是完成系统架构设计和数据库设计，确定后续实现必须遵守的模块边界、数据关系和扩展标准。

本阶段重点：

- 新闻、论文和专利三个模块的职责及物理隔离方式。
- 可插拔数据源适配器的统一协议与注册机制。
- 监控任务、模块、来源、运行记录和资源之间的数据关系。
- 三类资源的标准字段、专业字段、去重身份和历史保留原则。
- 增量游标、失败记录、来源隔离和未来调度所需的数据结构。
- MySQL 关系数据库的表结构、约束、索引和扩展边界。
- 面向外部系统的采集任务接口和数据库查询 API 边界。
- 服务端部署形态以及采集引擎、数据库和 API 层的职责分离。

以下内容明确延期，不作为当前阶段的设计重点：

- 前端页面布局和视觉样式。
- 数据看板、趋势图和交互式分析页面。
- 用户在前端查看结果的具体呈现形式。
- 前端报告阅读和通知交互。
- 每小时、每日、每周和自定义 Cron 等细粒度调度配置。
- 完整的后台调度器及其运维管理功能。
- 通知方式和通知策略的具体实现。
- 用户、企业、组织、角色和数据权限系统。
- 面向终端用户的账户注册、登录和多租户隔离。

## 7. 第一阶段系统边界

第一阶段系统由以下三个核心部分组成：

1. 采集服务：接收关键词和采集范围，调用对应模块与来源适配器获取数据。
2. MySQL 数据库：保存来源配置、监控任务、运行记录以及新闻、论文和专利资源。
3. 数据 API：向其他系统提供采集结果、任务状态和必要的数据库查询能力。

第一阶段不直接向企业或学者提供完整应用，而是提供可以被其他业务系统集成的后端数据服务。

## 8. 当前设计原则

- 来源与资源分离：来源配置不等于采集结果。
- 任务与资源分离：同一资源可以被不同关键词任务发现。
- 任务与来源是多对多关系：一个任务可以使用多个来源，一个来源也可以服务多个任务。
- 来源必须归属于明确的业务模块；任务只能选择其已选模块下的来源。
- 模块物理隔离：新闻、论文和专利使用独立采集器目录和资源表。
- 增量优先：周期执行时尽量避免重复抓取和重复入库，同时不得因游标提前推进而漏数据。
- 来源失败隔离：单个来源失败不能阻止其他来源完成采集。
- 采集器与调用方解耦：采集服务不依赖特定前端或用户系统。
- 数据库不直接暴露给外部调用方，统一通过服务 API 访问。
- API 层、采集执行层和持久化层应保持明确职责边界。

## 9. 待确认事项

- 用户最终查看和获得结果的主要形式暂不讨论，留待前端阶段确认。
- 一个监控任务是否允许配置关键词别名、同义词和排除词。
- 每个用户是否拥有独立的任务、数据权限和来源配置。
- 定时周期的具体选项和调度策略留待后续阶段确认。
- 数据相关性的判定标准和低相关数据的处理方式。
- 是否需要邮件、企业微信、钉钉或其他更新通知。
- 是否需要自动摘要、实体提取、趋势分析和报告生成。
- 数据 API 是否同时负责创建和管理采集任务，还是只提供结果查询。
- 第一阶段 API 的鉴权方式和网络访问边界。
