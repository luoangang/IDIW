# DeepSeek 多语种检索词规划器：下一阶段方案

日期：2026-10-13。

状态：仅规划，等待用户授权实施。模型服务已确定使用 DeepSeek。本文件不代表功能已经接入；本次不修改代码、插件、数据库、采集配置或定时任务，不调用付费模型接口。

## 1. 已确认需求

- 用户输入一个主题关键词，平台根据各采集来源的语种，准备合适的翻译和同义表达。
- 优先保持资料召回量；保留用户原词与手工别名，不由 AI 改写监控主题或删除已有资料。
- AI 能力属于平台公共服务，不要求每个爬虫包自行调用 DeepSeek。
- 第一版限定中英文，先适配通用 RSS 与 Google 新闻 RSS，其他插件随后按自身检索能力接入。
- 不将该组件叫作“具身智能模型”：它是检索词规划器，负责语言和词表，不负责浏览器点击、爬虫执行、文章相关性判断或周报生成。

## 2. 架构位置

```text
用户主题、手工别名、选中的采集来源
                 |
                 v
来源语种画像：配置 / RSS 标记 / 已有内容的本地识别
                 |
                 v
检索词规划器：读取有效缓存，缺失时请求 DeepSeek
                 |
                 v
结构校验、归一化去重、限制扩展范围、保存计划版本
                 |
                 v
按来源能力编译本次 query / aliases / 已声明 parameters
                 |
                 v
已有调度与执行器 -> 爬虫包 -> 原始包表与任务匹配关系
```

规划器无数据库写入、脚本执行和爬虫调用工具权限。平台控制输入、校验、持久化与执行，模型只返回检索词候选。

建议未来代码职责划分为 provider（DeepSeek 请求）、planner（计划与缓存）、source profile（语种和能力）、compiler（生成插件请求）。这是实现时的职责边界，不要求现在创建四套框架或新增多智能体系统。

## 3. 来源语种画像

### 判断顺序

1. 用户或插件维护者明确配置的检索语种优先，可配置多种语种。
2. 读取 RSS/Atom 的语言信息以及已采集记录的 `language`；忽略明显无效的标记。
3. 没有标记时，用已有标题、摘要的小样本做本地中英文识别，记录依据。
4. 无法确定时标记 unknown，不让模型仅凭域名、国家或网址猜测。第一版保留原词并使用中英双语词表作为可见的兜底策略。

语种识别主要由配置和本地检测完成，DeepSeek 负责根据已确认的目标语种翻译和扩词。这比每个来源都请求一次模型更容易控制。后续如需 AI 辅助语种判断，再单独评估小样本文本的外发边界。

### 需要区分的属性

- `content_languages`：来源文章使用的语种。
- `query_languages`：来源搜索接口接受或优先使用的语种。
- `mode`：订阅后筛选、原生关键词搜索、整站采集、精确标识查询或文件解析。
- Google 的地区配置和检索语言是不同属性，不从英文自动推断美国，也不由模型修改国家参数。
- 一个通用 RSS 包包含多个订阅地址，其画像应按地址记录，不能把整个包强行标记成一种语言。

第一版对多语种 RSS 合并所需语种的词表进行本地匹配；按每个 feed 使用不同词表可在后续优化，不影响现有 `feed_urls` 配置。

## 4. 检索词的分层

| 类型 | 含义 | 默认处理 |
| --- | --- | --- |
| original | 用户原词和手工维护的别名 | 保留，AI 不覆盖 |
| translation | 尽量准确的目标语种翻译 | 校验后启用 |
| synonym | 同一概念的常见表达、必要缩写 | 校验后启用，并能人工修改 |
| related | 上下游、较宽泛的关联概念 | 生成建议但默认不自动启用 |

举例：

- “具身智能”：英文等价/同义候选 `embodied AI`、`embodied intelligence`；`physical AI` 可作为关联建议，不默认声称完全等价。
- “军事智能体”：英文候选 `military AI agents`、`AI agents for military applications`；不能直接拆成单独的 `AI`、`military`、`agents` 做宽泛 OR 检索。
- 专利号、DOI、文献唯一标识不翻译、不扩词。整站模式和文件解析模式默认跳过检索词生成。

不能只看 JSON 格式合法就认定语义正确。第一版上线前人工审核两个重点主题的生成词表，对不准确的关联词禁用或纠正。

## 5. 平台内部计划格式

下列 JSON 仅为平台内部设计示例，未加入当前爬虫协议，不直接原样交给旧插件：

```json
{
  "plan_version": 1,
  "original_query": "具身智能",
  "target_languages": ["zh", "en"],
  "terms_by_language": {
    "zh": [
      {"term": "具身智能", "kind": "original", "origin": "user"}
    ],
    "en": [
      {"term": "embodied AI", "kind": "translation", "origin": "deepseek"},
      {"term": "embodied intelligence", "kind": "synonym", "origin": "deepseek"},
      {"term": "physical AI", "kind": "related", "origin": "deepseek"}
    ]
  },
  "enabled_kinds": ["original", "translation", "synonym"],
  "provider": "deepseek",
  "prompt_version": "query-plan-v1",
  "input_hash": "computed-by-platform",
  "state": "ready"
}
```

平台补充真实模型名、生成时间、版本、用量、人工覆盖项等元信息。模型输出只承担词表部分，不能自行填写可信的状态、费用、哈希或版本。

校验至少包含：合法 JSON、重复键检测、必需字段、语种范围、字符串类型、控制字符、长度、词数、空值、去重和主题原词一致性。建议模型每种语言的翻译/同义词最多 5 个，关联建议最多 3 个；这些是待实现的默认约束，不限制已有手工词表。

统一大小写、全半角、标点的去重规则，同时保留原始显示文本。词表是数据，不允许模型生成可执行代码、SQL、浏览器步骤或直接使用的搜索语法。网站特有语法由插件确定性转换。

## 6. 兼容现有插件协议

当前请求有 `query`、`aliases`、`parameters`，Schema 不允许任意新增顶层字段。第一版利用这些现有字段，不直接给所有包增加 `query_plan`、`languages` 等未知字段。

平台内部始终保留原始主题。针对来源选择目标语种主词时，实际插件请求的 `query` 可以是该主题的准确译文；这不是修改 `monitors.query_text`。其他可用表达放入 `aliases`。用户可在后续界面查看“监控主题”和“实际来源检索词”的区别。

| 包 / 模式 | 当前情况 | 计划适配 |
| --- | --- | --- |
| 通用 RSS，keywords 模式 | 已将 query、aliases 与手工扩展词用于标题/摘要/RSS 内容匹配 | 合并已启用的中英词表，保留手工配置；不额外下载每个网页全文 |
| 通用 RSS，all 模式 | 不按主题筛选 | 跳过 AI 词表，不改变整站采集行为 |
| Google 新闻 RSS | 当前只用 query 构建搜索 URL，aliases 被忽略 | 包内支持多词搜索、URL 去重、共享总上限；首版每次最多 3 个有效检索表达 |
| 百度百科 | 精确中文主题查词条 | 初期保持当前行为，不把宽泛关联词当作多个百科实体 |
| Wikipedia | 中文查询，英文回退仍用同一个 query | 后续支持独立的中英文等价主词；如需参数必须先在包的参数 Schema 声明并升级包版本 |
| 专利号 / DOI / 文件解析 | 不适合语言扩展 | 保留原始标识或文件参数，跳过该功能 |

Google 的多词请求发生在同一次插件执行内，合并后仍遵守本次 `limit`、时间范围和截止时间，不能将条数上限乘以词数。实际站点搜索能力须做联网验收，不承诺扩词后覆盖全部历史文章。

旧包继续运行；没有明确画像或扩词能力的包采用原词回退，不假称已完成多语种检索。

## 7. 计划存储和版本

尽量沿用当前数据库，不改变“每个爬虫包一张原始结果表”的原则，不改任务与资源的匹配关系。

建议实施时只做以下最小增量，当前不执行迁移：

| 位置 | 计划用途 |
| --- | --- |
| `monitors.query_text` | 继续存用户原始主题 |
| `monitors.aliases_json` | 继续存用户手工别名，不被模型覆盖 |
| 拟新增 `monitors.query_plan_json`，可为空 | 当前有效 AI 词表、输入哈希、版本、状态、人工覆盖、用量与错误摘要 |
| 拟新增 `crawler_packages.search_profile_json`，可为空 | 平台管理的来源语种/能力画像，通用 RSS 按地址保存覆盖项 |
| `monitor_runs.request_snapshot_json` | 保存本次计划版本/哈希和原始主题，使当次采集可追溯 |
| `package_runs.request_snapshot_json` | 继续保存发给该包的完整合法协议请求，不混入额外顶层字段 |

来源画像与爬虫的 `default_config_json` 分开，避免把未声明的管理元信息塞进受参数 Schema 校验的插件配置。密钥也不存进这些 JSON 字段。

后续如需要完整 AI 调用历史、复杂成本审计或跨任务缓存，再评估独立记录表；首版不增加多张分析表。

## 8. 缓存、并发与调用时机

- 创建/编辑主题或显式刷新计划时才生成，日常采集优先复用有效计划。
- 缓存键涵盖主题、相关领域上下文、影响生成的手工词表、目标语种集合、模型和提示词版本；相同来源增减但语种集合未变化时，不必重复请求模型。
- 展示/启用关联词属于本地选择；已有词表能满足时，不因一次开关变化重新生成。
- 冷启动或计划失效时可以先用原词和手工别名正常采集，异步生成新的计划，后续任务使用。
- 同一计划的并发生成应合并，设置全局请求并发限制，避免多个每日任务重复付费。
- 关键词更新后，旧请求返回的结果不能覆盖新主题计划：发布前核对输入哈希/版本。
- 外部模型调用不能放在当前 `enqueue_monitor` 的数据库事务或行锁中；先准备计划，入队时仅读取已提交的有效版本。

只有对缓存和计划版本做快照，才能解释同一个主题为什么某天使用了一组不同的检索词。

## 9. DeepSeek 接入边界

拟采用官方 API，模型名、地址、超时与限额可配置。API Key 仅通过服务器环境/密钥管理提供，不放入仓库、插件包、请求快照或网页响应，不需要在聊天中提供。

建议配置项：`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`，以及平台侧超时、最大输出 token、并发与预算限制。模型名在正式实施时重新核对可用型号，不依赖长期不变的旧模型别名。

DeepSeek 官方文档说明其 API 格式兼容 OpenAI/Anthropic；这只是接入格式，首版并不需要接入第二个模型服务。[首次调用 API](https://api-docs.deepseek.com/zh-cn/)

结构化词表可使用 JSON Output；官方要求配置 `response_format`、在提示中说明 JSON 输出并提供示例，以及合理设置输出长度。官方也提醒可能出现空内容，因此仍需平台侧深度校验与回退，JSON Output 不等于保证词表语义正确。[JSON Output](https://api-docs.deepseek.com/guides/json_mode/)

第一版只外发主题、必要的语义范围和目标语种，不外发完整采集数据库、正文、身份信息或内部配置。来源语言的小样本检测留在本地。

## 10. 失败回退与开销控制

- 没有密钥、接口超时、限流、网络失败、预算耗尽：保留既有有效计划；没有有效计划时使用原词与手工别名。
- 空响应、格式错误、过长或明显偏题的词表：不发布，不覆盖旧词表，记录可读错误。
- 可以设置有限重试和退避；建议首版最多一次重试，不无限修复提示或循环请求。密钥错误不重试。
- 旧计划只在原始主题仍一致且策略允许时作为回退；不能把旧主题的英文译词用于已经改名的新主题。
- 记录模型、提示词版本、请求耗时、调用数和实际返回的 token 用量；实施时按当时价格估算费用，不在规划文档固定价格。
- 限制新增词数和原生搜索请求数，避免模型调用便宜但扩展出大量网站请求。
- 缓存、回退和按语种复用可以减少额外开销；实际延迟、费用和覆盖增量需要实测，不承诺零负担。

## 11. 验收计划

### 离线验收

- 中英词表、重复词、全半角和大小写、术语缩写、专利号/DOI不变。
- 不覆盖用户主题和手工别名，关联词默认禁用。
- 不确定/混合语种、来源切换、缓存复用、主题更新、并发生成的旧结果拒绝。
- 超时、空 JSON、重复键、超长词、非法字段、429、鉴权失败和预算回退。
- 原协议请求仍通过校验，旧包不受影响；RSS all 模式不被误改成主题过滤。
- Google 多词搜索共享本次上限、去重和截止时间。

### 联网与相关性验收

1. 用“具身智能”和“军事智能体”分别生成一次中英词表，由用户检查准确性。
2. 在相同 RSS 输入快照上比较扩词前后候选，避免把来源更新混成扩词效果。
3. 将翻译/等价词新增命中与宽泛关联词新增命中分开，记录额外带来的有效文章数。
4. Google 搜索 RSS 另做真实站点检索验收，记录每个实际查询、返回量、重复量和耗时。
5. 将语言覆盖与相关性分开评估。当前已知具身主题明显误收约 5.1%，军事主题约 21.1%；扩词不应被宣传成已经解决误收，更不能保证自动降到 10% 以下。
6. 后续若启用文章相关性评审/周报筛选，作为独立阶段验收，保持原始资料可追溯。

## 12. 建议实施顺序

1. 加入来源画像、内部计划格式、缓存与完全可测试的模拟 provider，不影响现有采集。
2. 接入 DeepSeek 官方 API、严格输出校验、预算和错误回退。
3. 先适配通用 RSS，再升级 Google 新闻 RSS 的别名检索；以小规模真实任务验证。
4. 增加桌面端“原词 / 自动翻译 / 同义词 / 关联词”的预览、手工调整、刷新与状态显示。
5. 根据验证结果接入 Wikipedia、论文关键词检索等其他包；精确标识查询保持原样。

本轮交付仅为这份计划。实际代码、数据库迁移、密钥配置和付费 API 试运行留到下一步。
